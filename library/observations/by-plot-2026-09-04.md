## Why this exists

The catalogue entry for this endpoint carried `notes: "Response fields await a source-backed
contract."` and provenance `repository-brief`, which claims the **path** and disclaims the **shape**.
`library/decisions.md` requires a contract to stay empty until an official spec or a repository-made
observation supplies fields. **This is that observation.**

An earlier draft of this file said 10 nulls in its heading while listing 8, and the contract was built from the enumerated list rather than the heading. A document that disagrees with itself is the defect this project keeps paying for — corrected here rather than worked around downstream.**

**This is the single-sample trap and it must not be papered over: a `null` tells you the field EXISTS
and nothing about its type.** A contract that records these as `null` would reject the first listed
plot it ever sees. **Settling them needs a plot that is listed on the market, one under construction,
and one with a castle or keep** — at least three further samples, chosen for those states rather than
at random.

## valueClass

`data.player` is the only **name**-classed path — the account that owns the plot. **Its value is
deliberately not recorded here.** Under this repo's absolute rule no account name enters the
repository, so any fixture built from this observation carries a synthetic
`__synthetic_player__` value.

Everything else is `id`, `numeric`, `enum` or `timestamp`. **`land_stats` and `stats` are strings that
may carry structured content** — not inspected, and not to be classed until they are.

## What this observation does not settle

- The 10 null-typed fields above.
- Whether the endpoint's `status` field can read `"success"` while `data` carries an error — this API
  is recorded elsewhere as doing exactly that, and the client does not currently read that field.
- Behaviour for a non-existent plot id, an unowned plot, or a malformed id. **Three more calls.**

**Sampled plot ids 13339, 1, 500, 5000, 25000, 50000, 99000, 140000 — chosen to spread across the map

**`listing_price` is the one that justifies this whole exercise.** A contract written from reasoning would
have declared it `numeric` — it is a **quoted string**. A `valueClass` of `numeric` on a string field
either rejects every listed plot or silently coerces a price, and a price is the field where silent
coercion matters most.

**`castle` and `keep` remain unsettled and must stay undeclared.** Eight samples is not proof of absence
— it is proof that no plot among these eight has one. **Do not declare them `null`; a contract that does
will reject the first castle it meets.**

## A third finding, unlooked for: how a non-existent plot answers

**Superseded 2026-09-05:** The observation below recorded plot ids 75000 and 120000 returning HTTP 200
with `data: null`. A later repository-made call found that non-existent plots now return HTTP 200 with
the `data` key absent. The earlier record remains evidence of the response shape observed on that date.

**That is the real shape of the "genuine empty result" case**, and it matters for the tool's error
vocabulary: `upstream_empty` must be a *successful* result with zero rows, because the upstream itself
calls this success. **An implementation that treats a null `data` as a failure would report "we could not
ask" about a plot that simply does not exist — conflating two of the three outcomes the vocabulary exists
to keep apart.**

## Third pass: the exact cause of the live `upstream_malformed`, and it was my own single-sample error

**A diagnosis lane established from source that the validator ignores additive keys entirely, so a
41-key body cannot fail for having extra fields — it can only fail on a missing required path or a
DECLARED path whose type differs. It correctly refused to name which, because this file recorded only
the six newly non-null fields rather than all 42 types. That gap was mine. Closed by a full path/type
diff of both plots:**

**Both bodies have exactly 42 paths. Nothing is additive. Eight paths diverge in type, and they split
into two groups that matter very differently:**

**Group A — six paths that were null in 13339 and carry values in plot 1** (`listing_price`,
`market_id`, `market_listing_id`, `market_listing_status_id`, `market_updated_date`, `unlock_date`).
**These are harmless: they were deliberately left UNDECLARED, so the validator never inspects them.**
That decision was correct and is now proven correct.

**Group B — THE CAUSE. Two paths that were TYPED from the 13339 sample and are NULL in plot 1:**

| Path | 13339 | plot 1 |
|---|---|---|
| `data.resource_id` | `int` | **null** |
| `data.resource_symbol` | `str` | **null** |

**Those two are declared, so a null fails the declared-type check and the whole body is reported
`upstream_malformed`.** A market-listed plot has no resource assigned — which is obvious once seen and
was invisible from one sample.

**THE LESSON IS THE ONE THIS FILE ALREADY WARNED ABOUT, APPLIED TO THE FIELDS IT DID NOT WARN ABOUT.**
The first pass said plainly: *a `null` tells you the field EXISTS and nothing about its type*, and it
flagged eight such fields. **It did not consider the reverse — that a field with a real value in one
sample can be null in another. Same trap, opposite direction, and the warning was already written.**

**REMEDY: `resource_id` and `resource_symbol` must be declared as nullable, or undeclared like group A.
Not retyped from a second guess.** And the general rule this earns: **a type derived from a single
sample is a hypothesis. Two samples that disagree are worth more than ten that agree.**
